# 0020. HTTP 입구: 출처 인증, 오류 형식, JSON 읽기

상태: 확정 (2026-10-22)

## 결정

출처 인증

- 허용 출처([0013](0013-grade-identification.md))마다 256비트 무작위 token 을 발급한다. 설정 파일에는 token 의 SHA-256 만 둔다.
- 요청은 TLS 안에서 `Authorization: Bearer <token>` 으로 받는다. 받은 값의 SHA-256 을 등록된 값과 상수 시간으로 비교한다.
- 같은 출처의 인증 실패가 연속으로 이어지면 그 출처를 잠시 잠그고, 인증 실패는 감사 메타데이터로 남긴다.

오류 형식

- 거절과 오류는 Chat Completions 호환 `error` 객체로 돌려준다. `code` 에는 사유 코드 이름(예: `entity_blocked`)을, 차단 종류가 있으면 종류 이름만 넣는다.
- 차단 위치, 원문, provider 오류 본문과 헤더는 응답에 넣지 않는다. 위치는 감사 메타데이터에만 둔다.

JSON 읽기

- 요청과 provider 응답은 nlohmann-json 의 SAX 방식으로 읽는다. 핸들러가 허용 필드([0017](0017-request-response-boundary.md)) 밖의 키, 중복 키, 깊이 16 초과를 만나면 즉시 읽기를 멈추고 거절한다.
- 숫자 범위 넘침(`1e400` 등)과 잘못된 UTF-8 은 라이브러리가 거절한다. 라이브러리 예외는 입구에서 값으로 바꾼다.
- 본문 크기 상한은 HTTP 단계에서 먼저 막는다.

응답 역할 문자열

- 이전 모델 응답의 역할 이름은 API 가 정한 문자열 그대로 써야 하지만 공개 정책의 금지 표현과 겹친다. 소스에는 이 문자열을 바이트 배열 상수 한 곳에만 둔다. 설정 항목으로 두지 않는다.

## 대안

| 대안 | 거절 이유 |
|---|---|
| mTLS 클라이언트 인증서 | 더 강하지만 인증서 발급·교체 절차가 필요하다. 배포(Phase 13) 때 다시 본다 |
| 자체 오류 형식 | 기존 클라이언트 SDK 가 오류로 인식하지 못한다 |
| Boost.JSON | 중복 키를 막는 선택지가 없어 저수준 핸들러를 직접 써야 하고, `1e400` 을 무한대로 받아들인다. 의존성이 하나 늘어난다 |

## 근거

결정 #111. JSON 라이브러리는 같은 입력으로 비교했다(boost-json 1.92.0, nlohmann-json 3.12.0, clang-cl Release).

| 입력 | nlohmann-json | Boost.JSON |
|---|---|---|
| 중복 키 | 마지막 값(막는 선택지 없음, SAX 로 막음) | 마지막 값(막는 선택지 없음) |
| 잘못된 UTF-8, 서로게이트, NUL, 주석, NaN, 뒤 문자 | 거절 | 거절 |
| `1e400` | 거절 | 무한대로 받아들임 |
| 깊이 64·1000 | 받아들임(상한 없음, SAX 로 막음) | 거절(기본 상한 32) |
| 깊이 100,000 | 파싱·해제는 되고 다시 출력할 때 스택 넘침 | 상한을 풀면 스택 넘침 |
| 2.6 MB 파싱 | 14.2~17.9 ms | 8.0~8.7 ms |

요청 본문 상한(64 KiB) 안에서는 속도 차이가 1 ms 미만이다.

## 보안 영향

- token 원문은 저장하지 않아 설정 파일이 새도 바로 쓸 수 없다. token 자체를 빼앗기면 그 출처로 요청할 수 있으므로 TLS 와 잠금으로 보완한다.
- 사용자 응답에는 차단 종류만 나가므로 어느 위치가 걸렸는지를 반복 요청으로 알아내기 어렵다.

## 변경 조건

- 기관이 클라이언트 인증서 체계를 이미 운용하면 mTLS 를 다시 검토한다.
