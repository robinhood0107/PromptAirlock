# 0028. 문서 입력: 별도 추출 프로세스

상태: 확정 (2026-11-02, Phase 11.5-1. 2026-11-03 11.5-2 에서 hwp 5.0·PDF 를 더함. 게이트웨이 연결은 11.5-3 에서 더한다)

## 결정

문서 파일 해석은 게이트웨이 프로세스 안에서 하지 않는다. 요청마다 추출 실행 파일 `prompt-airlock-extract` 를 자식 프로세스로 띄워 파일 byte 를 표준 입력으로 넘기고, 버전 붙은 JSON 을 표준 출력으로 받는다.

| 쪽 | 하는 일 |
|---|---|
| 추출 실행 파일 | 시작하자마자 자기 자원을 제한하고(아래 표), 실패하면 해석하지 않고 끝난다. 형식을 판별해 글자 덩어리와 위치, 뺀 부분 수, 또는 거절 사유를 JSON 한 줄로 쓴다 |
| 실행기(`extract_in_child`) | 상속 핸들을 파이프 셋으로 제한해 띄우고, 쓰기·읽기 스레드로 입출력, 시간 상한·출력 상한·취소 가운데 먼저 오는 것에서 자식을 죽인다. 자식 stderr 는 버린다. 0 이 아닌 종료와 약속과 다른 출력은 실패다 |

자식의 자기 제한

| 자원 | Windows(자기를 Job Object 에 넣음) | Linux(setrlimit) |
|---|---|---|
| 메모리 | 프로세스 메모리 1 GiB | 주소 공간 1 GiB |
| CPU 시간 | 30 초 | 30 초 |
| 자식 프로세스 | 활성 프로세스 1개(자기만) | NPROC 0 |
| 파일 쓰기 | (쓰는 코드 없음) | FSIZE 0 |
| 열 수 있는 파일 | - | 16 |
| 코어 덤프 | - | 0 |

- sanitizer 시험 빌드는 그림자 메모리를 크게 예약하고 끝날 때 LeakSanitizer 가 fork 하므로 메모리 제한과 Linux 프로세스 수 제한을 걸지 않는다(제품 빌드에는 걸린다).
- 부모의 시간 상한은 벽시계 30 초다. 상한은 받은 문서 146개를 재고 #226 에 측정 전에 고정했다(파일 32 MiB, zip 항목 1,000, 항목 64 MiB, 풀린 합 128 MiB, 압축률 100, 깊이 2, 안의 문서 64, XML 깊이 256, 뽑은 글자 8 MiB).

형식(이 단계)

| 형식 | 판별 | 뽑는 것 | 세기만 하는 것 |
|---|---|---|---|
| txt·csv·md | 매직 없음, 확장자 | 줄 | |
| htm | 확장자 또는 `<!doctype html`·`<html` | 태그를 뺀 줄, 문자 참조 풀기, 표 칸은 탭 | script·style·주석은 버림 |
| docx | zip 안 `word/document.xml` | 문단(표 칸 포함), 끼워 넣은 변경 | 메모, 지운 변경, 숨긴 글(vanish), 머리글·바닥글·각주·문서 속성 |
| xlsx | `xl/workbook.xml` | 보이는 시트의 행(칸은 탭), 공유 문자열, 바로 쓴 문자열, 숫자 | 숨긴 시트·행, 메모, 문서 속성, 발음 표기 |
| pptx | `ppt/presentation.xml` | 슬라이드 순(숫자 순) 문단 | 숨긴 슬라이드, 노트, 메모 |
| hwpx | `mimetype` 이 `application/hwp+zip` | 구역 순 문단(표 안 문단 포함) | 메모, 미리보기 |
| HWPML(한글 XML 2.x, 확장자 hwp 로도 옴) | 글이 `<?xml` 로 시작하고 `<HWPML` 이 있음 | 문단(P)의 CHAR 글자 | 숨은 설명(HIDDENCOMMENT) |
| 그 밖의 XML | 글이 `<?xml` 로 시작 | 거절(unsupported). 마크업째 보내지 않는다 | |
| zip | 위에 해당 없는 zip | 안의 문서(깊이 2) | 그림 등 해석하지 않는 항목 |
| hwp 5.0(CFB) | `D0 CF 11 E0` + `FileHeader` 스트림 | `BodyText/Section*` 의 문단 글자(PARA_TEXT), 표 안 문단 포함 | 머리글·바닥글·각주·미주(다른 부분), 숨은 설명(메모) |
| doc·xls·ppt(CFB) | `D0 CF 11 E0`, `FileHeader` 없음 | 거절(legacy_format, 새 형식으로 저장해 달라고 안내) | |
| PDF | `%PDF-` | 쪽마다 글자 층(PDFium), 2,000쪽까지 | 주석(메모) |

인코딩
- BOM(UTF-8, UTF-16LE·BE) → 올바른 UTF-8 → CP949 순서로 본다. NUL 이 있으면 글자 파일이 아니다.
- CP949 표는 `tools/gen_cp949_table.c` 로 glibc iconv 에서 만든 17,048자다. Windows 코드 페이지 949 와 대조해 같았고, Windows 만 가진 사용자 정의 영역 188자(사설 영역 글자)는 넣지 않았다. 표는 글자 대응이라는 사실 정보이고 glibc 코드를 담지 않는다.
- zip 항목 이름이 UTF-8 이 아니면 CP949 로 풀고, 그래도 안 되면 번호(`entry3`)로 부른다.

hwp 5.0
- CFB(복합 문서)는 직접 읽는다. FAT·작은 FAT·디렉터리 사슬은 범위와 순환을 검사하며 따라가고, 적힌 크기보다 짧은 사슬은 손상이다.
- FileHeader 속성 비트로 암호(1)·배포용(2)·DRM(4)·공인인증서 암호화(8)·공인인증서 DRM(10)을 알아보고 encrypted 로 거절한다. 판이 5 가 아니면 unsupported.
- 본문 스트림은 머리 없는 deflate 이고, 풀린 크기·압축률은 zip 과 같은 상한으로 본다.
- 문단 글자는 UTF-16 이며, 조판 제어 문자 가운데 글자 하나짜리(0, 10, 13, 24-31)는 1 단위, 나머지는 8 단위를 차지한다. 탭은 탭, 줄 바꿈은 빈칸으로 바꾸고 나머지 제어는 버린다.

PDF(결정 #229)
- PDFium 을 공식 소스(커밋 b75764a1)에서 우리가 빌드해 추출 실행 파일에만 정적으로 링크한다. 빌드 설정: V8·XFA·Skia 끔, 완전한 정적 라이브러리, 시스템 C++ 표준 라이브러리. 추출기의 주소 공간 제한(1 GiB)과 부딪혀 Chromium 할당기(PartitionAlloc)와 malloc 대체를 끄고, GNU ld 가 읽지 못하는 ELF CREL 재배치를 켜는 빌드 설정 한 줄을 지운다(PDFium 코드는 그대로).
- 빈 사용자 암호로 열리는 암호 PDF 는 읽는다(받은 PDF 27개가 이 꼴). 암호가 필요하거나 모르는 보안 처리기면 encrypted.
- 글자가 없는 쪽만 있으면(스캔본) no_text. OCR 은 하지 않는다.
- PDFium 경로(`PA_PDFIUM_DIR`)를 주지 않고 빌드하면 PDF 는 unsupported 다(CI 기본).

거절과 빠뜨림
- 암호화한 zip 항목, hwpx manifest 의 암호화 정보(배포용 문서 포함)는 encrypted.
- 안에 든 문서 하나라도 못 읽으면 묶음 전체를 거절한다. 읽은 것만 보내면 사용자가 빠진 줄 모르고, 못 읽은 문서에 든 값이 검사 없이 뒤의 경로로 갈 수 있는 틈을 만들지 않기 위해서다.
- XML 은 DOCTYPE·개체 선언이 보이면 바로 멈춘다(외부 개체, 개체 확장 공격). Office·hwpx XML 은 DOCTYPE 를 쓰지 않는다.
- HWPML 은 DOCTYPE 안에 `<!ENTITY nbsp "&#160;">` 를 둔다. HWPML 만, 외부 DTD 가 없고 값이 32 byte 이하이며 `&`·`<`·`%` 가 없는 내부 개체를 64개까지 받는다. 값이 다른 개체를 부를 수 없으니 확장이 커질 수 없다.
- 적힌 크기보다 더 풀리는 항목은 폭탄으로 본다.

라이브러리
- libzip 1.11.4(BSD-3-Clause, 기본 기능 끔: 압축은 zlib deflate 만, AES 없음), Expat 2.8.5(MIT), zlib 1.3.2(Zlib). 셋 다 추출 실행 파일과 시험만 링크한다. 게이트웨이는 실행기와 JSON 만 링크한다.

## 근거

- 파일 해석기는 공격 입력을 가장 많이 받는 코드다. 같은 프로세스에서 해석하면 해석기 결함 하나로 가명 범위, provider 자격 증명, 감사 기록 키가 있는 메모리에 닿을 수 있다. 별도 프로세스와 자원 제한은 결함이 있어도 피해를 그 프로세스 안에 가둔다.
- 요청마다 새 프로세스라 한 요청의 파일 내용이 다음 요청에 남지 않는다.
- 자기 제한은 Windows·Linux 에서 같은 모양이다(부모가 따로 제한을 걸 때 생기는 "자식이 이미 시작한 뒤" 틈이 없다). 해석은 제한을 건 뒤에만 시작한다.
- 받은 문서로 처음 돌려 본 결과(11.5-1, 공개는 집계만): hwpx 22개 중 19개 추출, 3개는 manifest 에 실제 암호화 정보가 있어 거절. xlsx 2, htm 1 추출. 확장자 hwp 3개 가운데 1개는 HWPML 로 333문단 추출(처음에는 글자 파일로 읽혀 마크업째 나갈 뻔했고, 다음에는 DOCTYPE 거절로 손상 판정이 나서 위 두 규칙을 더함), 2개는 hwp 5.0 이라 11.5-2 전까지 거절. csv 5개 중 4개 추출, 1개는 글자 26 MB 로 출력 상한(8 MiB)에서 거절. zip 2개는 안에 PDF·hwp 가 있어 11.5-2 전까지 거절.

## 대안

| 대안 | 거절 이유 |
|---|---|
| 게이트웨이 안에서 해석 | 해석기 결함이 게이트웨이 비밀에 닿음 |
| 오래 사는 추출 프로세스 하나(작업 대기열) | 한 요청이 남긴 상태(메모리 조각, 오염된 해석기 상태)가 다음 요청에 이어짐 |
| 문서를 클라이언트가 글자로 바꿔 보냄 | 기관 앱마다 다르게 바꾸고, 숨긴 시트·메모까지 보내는 앱을 막을 수 없음(전송 최소화를 게이트웨이가 보장 못 함) |
| PDF 직접 구현(결정 #229) | 받은 PDF 111개 중 27개가 암호화, 99개가 CID 글꼴이라 암호·글꼴 처리를 직접 해야 하고, 암호 기능은 ADR 0014 와 부딪힘 |
| PDFium 미리 빌드본(결정 #229) | 제3자가 빌드한 실행 코드를 믿어야 함 |
| 컨테이너·seccomp 격리 | 설치형 Windows 대상에서 같은 방식으로 쓸 수 없음. Linux 추가 격리는 Phase 12 에서 검토 |

## 보안 영향

- 자식이 죽거나 늦거나 이상한 출력을 내면 그 요청은 거절되고 provider 는 불리지 않는다(11.5-3 에서 게이트웨이와 연결하며 시험).
- 자식은 네트워크·파일 쓰기 코드를 갖지 않는다. 그러나 운영체제 수준의 네트워크 차단은 아직 없다(Phase 12 검토 대상).
- 뽑은 글자는 원문이다. 감사 기록에는 형식·크기·해시·개수만 남긴다(11.5-3).

## 변경 조건

- 처리량이 문제되면(요청마다 프로세스 시작 비용) 측정 뒤 미리 띄운 일회용 프로세스 풀을 검토한다. 한 프로세스가 두 요청을 처리하지 않는 조건은 유지한다.
