# 0017. 외부 요청·응답 경계: 허용 필드, 복원 위치, 인코딩

상태: 확정 (2026-10-05). 출력 상한과 인코딩 깊이 초과 처리를 2026-10-05에 더했다.

## 결정

요청

1. 받는 endpoint는 `POST /v1/chat/completions` 하나다. 다른 경로는 거절한다.
2. 요청 필드는 아래만 받는다. 목록에 없는 필드가 하나라도 있으면 요청 전체를 거절한다.

| 필드 | 처리 |
|---|---|
| `model` | 받되 provider에는 Gateway의 고정 별칭을 보낸다 |
| `messages` | 역할은 `system`, `developer`, `user`와 이전 모델 응답 역할(API의 응답 역할 이름). `content`는 문자열 또는 `{"type":"text","text":...}` 배열. 그 밖의 content part(이미지, 오디오, 파일)와 `name`, `tool_calls`, `tool_call_id`는 거절 |
| `max_tokens`, `max_completion_tokens` | 상한 안으로 줄여 보낸다. 없으면 상한값을 넣어 보낸다. 둘 다 있고 값이 다르면 거절한다 |
| `temperature`, `top_p` | 범위 검사 후 보낸다 |
| `stop` | 문자열 또는 문자열 배열. 본문과 같이 검사한다 |
| `n` | 없거나 1 |
| `stream` | 없거나 `false`. `true`는 거절 |
| `response_format` | 없거나 `{"type":"text"}`, `{"type":"json_object"}` |

출력 상한

- 기본값은 4096 token이다. 기관이 설정으로 1~65536 안에서 바꿀 수 있다. 설정 항목의 이름과 검증은 설정 파일을 만들 때 정한다.

3. 모든 역할의 메시지와 `stop` 문자열을 하나의 검사 대상으로 묶어 검사한다. 크기 한도(64 KiB, [0015](0015-default-actions.md))는 이 전체에 적용한다.
4. provider 요청은 검증을 통과한 내용만으로 Gateway가 새로 만든다. 클라이언트 요청 헤더는 넘기지 않는다. provider 쪽 보관·상태 저장 플래그는 보내지 않는다.

응답

5. provider 응답은 허용한 필드(첫 choice의 `message.role`, `message.content`, `finish_reason`, `usage`)만 읽고 Gateway가 응답을 새로 만든다. `model`은 Gateway 별칭, `id`는 Gateway 요청 ID로 바꾼다. `tool_calls`, 이미지·오디오, `logprobs`가 있으면 응답을 거절한다.
6. provider 오류 본문과 응답 헤더는 클라이언트에 넘기지 않고 고정 오류 코드로 바꾼다. 오류 본문은 감사 기록에도 남기지 않는다.
7. 응답 처리 순서: 응답 검사(Block 종류의 원문 값이 응답에 새로 나타나면 거절) → token 찾기 → token 위치 판정 → 복원.
8. token이 다음 위치에 있으면 복원하지 않고 응답 전체를 거절한다.
   - 마크다운 링크와 이미지의 주소 부분, 자동 링크
   - `scheme://`로 시작하는 URL, `www.`로 시작하는 주소, `mailto:` 같은 scheme 주소
   - HTML 속성 값(`href`, `src`, `srcset`, `action`, `formaction`, `data`, `poster`, `background`)
   - `data:` URI, CSS `url()`
9. 그 밖의 위치에서는 같은 요청 범위에서 발급한 token만 정확히 일치할 때 복원한다([0008](0008-pseudonym-token-format.md)).

인코딩

10. 다음 인코딩으로 보이는 덩어리는 풀어서 같은 detector로 다시 검사한다: base64, base64url(16자 이상), hex(16자 이상 짝수), percent 인코딩(`%XX` 3개 이상 연속), HTML 숫자 문자 참조, `\uXXXX` 이스케이프. 푸는 깊이는 2단계까지다.
11. 푼 내용에서 가명화 대상이나 차단 대상이 나오면 요청 전체를 거절한다. 인코딩 안의 값은 가명으로 바꿔 넣지 않는다.
12. 풀어도 텍스트가 아니거나 깊이 2까지 풀어도 여전히 인코딩으로 보이는 덩어리는 원래 길이가 256자 이상이면 거절한다. 내용을 확인할 수 없는 덩어리이기 때문이다. 더 짧은 것(해시값 등)은 통과한다.

## 대안

| 대안 | 거절 이유 |
|---|---|
| 요청을 그대로 provider에 넘기고 본문만 검사 | 검사하지 않은 필드와 헤더가 그대로 나간다 |
| 모르는 필드를 지우고 나머지만 보냄 | 사용자가 의도한 동작이 조용히 바뀌고, 지운 필드의 내용이 무엇이었는지 판단할 수 없다 |
| URL 안의 token을 복원 | 기관 앱이 링크·이미지를 그리는 순간 원래 값이 외부 주소로 나간다 |
| URL 안의 token만 지우고 응답 전달 | 응답이 무엇을 하려 했는지 숨기게 되고, 주입된 지시가 다른 형태로 반복될 수 있다 |
| 스트리밍 응답을 조각 단위로 검사 | token이 조각 경계에서 잘리고, 검사 전 내용이 사용자에게 간다 |
| 인코딩 안의 값을 가명화 후 다시 인코딩 | 구현 오류 위험이 크고 그런 질의의 쓸모가 작다 |

## 보안 영향

- provider로 나가는 내용은 검사를 통과한 텍스트와 고정 파라미터뿐이다.
- 응답을 통해 원래 값이 외부 주소로 나가는 경로를 막는다.
- 도구 호출, 이미지·파일 입력, 스트리밍을 쓰는 기관 애플리케이션은 이 버전에서 쓸 수 없다.
- 인코딩된 덩어리와 링크가 섞인 응답이 거절될 수 있다. 거절 사유 코드로 구분한다.

## 변경 조건

- 스트리밍이 필요하면 응답 전체를 받아 검사한 뒤 보내는 방식으로 이 문서를 고친다.
- 이미지·파일 입력이 필요하면 별도 검사 경로를 결정한 뒤 허용 목록에 더한다.
- provider API 형식이 바뀌면 허용 목록과 시험을 함께 고친다.
