# 0014. 암호 사용 범위와 알고리즘

상태: 확정 (2026-10-05)

## 결정

1. Gateway와 Vault는 저장 데이터를 스스로 암호화하지 않는다. 감사 로그와 이력의 기밀성은 OS 접근 통제(관리자만 열람)와 기관이 운용하는 저장 암호화 제품(DB 암호화, 디스크 암호화)에 맡긴다. 무결성은 SHA-256 연결 해시로 확인한다. Vault 매핑은 메모리에만 둔다.
2. TLS는 기관 애플리케이션 방향과 외부 provider 방향 모두 쓰며 평문 옵션을 두지 않는다. 협상 범위는 다음으로 고정하고 설정으로 바꿀 수 없다.
   - 프로토콜: TLS 1.2, TLS 1.3
   - TLS 1.3: `TLS_AES_128_GCM_SHA256`, `TLS_AES_256_GCM_SHA384`
   - TLS 1.2: ECDHE-ECDSA 또는 ECDHE-RSA와 AES-GCM 조합
   - 키 교환 곡선: P-256, P-384
   - handshake 서명: ECDSA, RSA-PSS(2048비트 이상)
   - 인증서 체인: 공인 인증기관이 발급한 SHA-256 이상 서명을 검증한다. 체인 서명 방식은 상대 인증기관이 정하므로 handshake 서명과 따로 둔다.
   - 쓰지 않음: ChaCha20-Poly1305, X25519, SHA-1 서명, RSA 키 교환, CBC
3. 암호 기능은 한곳에 모은다. C++에서는 TLS 설정을 만드는 함수 하나(`src/tls/`)와 SHA-256 함수 하나만 OpenSSL을 부른다. Rust Vault는 OS 난수(`getrandom`)만 쓰고 암호 crate를 추가하지 않는다.
4. 가명 token과 Vault 연결 비밀값은 OS 난수로 만든다. 둘 다 암호 키가 아니며, 자체 난수나 암호 알고리즘을 구현하지 않는다.
5. 이 소프트웨어는 국가정보원 검증필 암호모듈(KCMVP)이 아니다. 문서에서 검증필 암호모듈 사용, 보안적합성 검증 같은 요건을 충족한다고 쓰지 않는다. 기관 도입 때 확인할 항목으로 남긴다.

## 대안

| 대안 | 거절 이유 |
|---|---|
| 상용 검증필 암호모듈을 Gateway와 Vault에 넣음 | 독점 라이브러리라 AGPL 배포와 충돌하고, 공급사·OS에 묶이며, 기관이 받아서 바로 쓰기 어렵다 |
| OpenSSL 기본 설정 그대로 사용 | 국정원이 확인하지 않은 알고리즘(ChaCha20, X25519)으로 협상할 수 있다 |
| TLS를 끄고 기관의 TLS 장비에 맡김 | Gateway 앞뒤에 평문 구간이 생기고, 평문 옵션 자체가 설정 실수의 원인이 된다 |

## 근거

쪽은 인쇄 쪽이다.

| 확인한 내용 | 근거 |
|---|---|
| 비밀이 아닌 업무자료를 암호화해 소통·보호할 때는 국정원장이 개발하거나 안전성을 확인한 암호알고리즘을 써야 한다 | 국가 사이버보안 기본지침 제128조 ①(p.115) |
| 국정원장은 비밀 아닌 업무자료 보호에 검증필 암호모듈 등을 활용토록 할 수 있고, 기관은 검증 유효기간과 정지 여부를 확인한다 | 기본지침 제22조 ①②(p.30) |
| 보안기능 있는 정보통신제품의 도입 요건(검증필 목록, 검증필 암호모듈 탑재, 보안적합성 검증 등) | 기본지침 제20조(p.27~28) |
| 암호기술을 쓸 때 등급과 용도에 따라 검증필 암호모듈을 쓴다(EA-1, C·S·O) | N2SF 부록1 보안통제 항목 해설서 p.85~86 |
| 외국과의 통신이 불가피하면 TLS 같은 국제 표준은 통제된 환경에서만, 외국산 암호 기술은 전용 네트워크나 게이트웨이 내부에서만 적용한다 | 부록1 p.86 |
| 공개등급 데이터는 데이터 암호화 대상에서 제외한다 | 국가ㆍ공공기관 보안 가이드북 M04(p.35) |
| 통신 구간은 인증을 강화하고 암호화한다 | 보안 가이드북 M18(p.39) |
| AES가 2026년 1월부터 검증대상 알고리즘에 포함된다. 모듈은 계속 검증을 받아야 한다 | 국가정보원 발표 보도(2024-09-11) |

- AES-GCM, P-256·P-384 ECDHE, ECDSA, RSA-PSS, SHA-2는 검증대상 알고리즘에 속한다. 그래서 위 협상 범위로 제128조의 알고리즘 요건을 맞춘다. 인증서 체인 서명은 상대가 고른 인증기관의 방식이라 이 범위에 넣지 않는다.
- OpenSSL은 검증필 암호모듈이 아니므로 알고리즘을 제한해도 모듈 요건은 충족하지 않는다.
- 외부 provider의 TLS 상대편은 기관이 고를 수 없다. 국제 표준 TLS를 Gateway 안에서만 쓰는 구성이 부록1의 구현 예시와 맞는다.
- 저장 암호화를 Gateway가 직접 하면 키 생성, 보관, 폐기(EK 계열)까지 떠안는다. 기관이 이미 운용하는 저장 암호화 제품 위에 두는 편이 설정과 관리 항목을 늘리지 않는다.

## 보안 영향

- provider가 위 협상 범위를 지원하지 않으면 연결이 실패하고 요청은 거절된다.
- 저장 기밀성은 기관의 저장 암호화에 의존한다. 설치 안내에 이력과 로그를 기관 암호화 볼륨에 두도록 적는다.
- 암호 코드를 한곳에 모아 다른 모듈이 임의로 TLS 설정을 만들거나 알고리즘을 바꿀 수 없다.

## 변경 조건

- 기관 보안성 검토에서 Gateway 자체에 검증필 암호모듈을 요구하면 TLS 설정 함수와 SHA-256 함수를 검증필 모듈로 바꾸는 결정을 따로 한다. 라이선스 예외 여부를 함께 정한다.
- 국정원 검증대상 알고리즘 목록 원문에서 위 협상 범위의 알고리즘이 빠져 있거나 바뀌면 범위를 다시 정한다.
- 국제표준 암호 인증을 정보통신제품 도입 요건으로 인정하는 지침 개정이 나오면 그 기준을 따른다.
